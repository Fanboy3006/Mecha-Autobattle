# 项目方向调整：以 Godot 为唯一长期维护的游戏引擎

## 一、最终目标

当前 JS 单文件游戏已经具备基本成立的玩法，包括战斗、战术卡牌、气力轮转、条件触发和肉鸽选牌。现阶段的核心目标不再是持续扩展 JS 游戏，而是将其迁移、重构为一个长期可维护的 Godot 项目。

**最终只维护一套正式游戏引擎：Godot。**

项目的最终交付目标是：游戏可以通过 GitHub Pages 等静态托管方式发布，让朋友打开链接就能直接游玩，不需要安装 Godot 或其他运行环境。

## 二、职责划分

### CC：Godot 架构与迁移负责人

CC 负责：

- 审计现有 JS 项目，识别真正需要迁移的玩法规则、状态、战斗逻辑、随机数、决策日志、录像重放、存档和 UI。
- 根据实际需要使用 AST、依赖分析等工具，降低代码定位和迁移成本。
- 设计 Godot 项目结构、模块边界、数据与逻辑分离方案，以及 Runtime 与 Presentation 的职责边界。
- 制定 JS 到 Godot 的迁移计划并负责架构落地。
- 建立 Godot 自身的测试、回归验证、构建和发布流程。
- 确保最终项目能够独立运行，并支持 Web 导出及 GitHub Pages 发布。

AST 是辅助工具，不是最终交付目标。不要为了建设庞大的分析工具链而偏离迁移目标。

### ARGON：Gameplay Architect

ARGON 负责：

- 解释和确认现有游戏的玩法语义。
- 在 CC 需要时提供战斗规则、卡牌行为、资源轮转、随机数和边界情况的说明。
- 判断迁移前后是否改变了原有玩法。
- 负责未来玩法设计与体验验收。

ARGON 不再推动与 Godot 迁移无关的 JS 玩法打磨，也不与 CC 重复开展架构调查。

### 用户

用户负责游戏体验判断、阶段验收及项目方向决策，不应被迫长期管理两套代码引擎。

## 三、迁移原则

1. **Godot 是唯一迁移目标。** 不以重构出一套更漂亮的 JS 架构为目标。
2. **现有 JS 只作为迁移参考。** 迁移期间可以只读、分析和必要时运行，用于确认已有玩法及对账。
3. **不再默认扩展旧 JS。** 除非某项修改是确认玩法语义或完成迁移所必需的，否则不为旧引擎增加新功能。
4. **不要求 JS 完美后才迁移。** 只需要弄清迁移必需的玩法规则；旧系统中的非关键缺陷不应成为迁移阻碍。
5. **优先建立 Godot 自身的验证体系。** 包括确定性测试、战斗结果校验、决策日志、必要的重放能力和回归测试。
6. **避免重复维护。** 不要求 JS 与 Godot 长期同步开发、同步修复或永久双引擎对账。
7. **尊重现有玩法。** 迁移阶段以保留已验证的玩法语义为原则；确实需要改变的规则必须明确记录并单独确认。
8. **保持交付可验证。** 关键阶段必须有实际运行结果、测试结果和 Web 导出验证，而不是只交付架构文档。

## 四、Replay、Decision Log 与旧系统缺陷的处理

现有 JS 项目可能存在录像重放、弹窗参数、战术卡牌候选记录或条件发牌失败记录等问题。

不要因为发现这些问题，就自动新增 JS 返工 Feature。

先判断这些问题是否会阻碍 Godot 迁移：

- 如果只是旧 JS 的辅助分析工具不够完善，而 Godot 可以直接建立可靠的测试与日志机制，则优先在 Godot 中解决。
- 如果某项缺陷导致关键玩法规则无法确认，则选择成本最低的可靠方法确认规则，必要时才修复旧 JS。
- 不要为了完善旧 JS 的录像和分析体系，推迟 Godot 迁移。
- 迁移过程中可以使用现有录像、战报、固定场景和人工验证作为参考，但不能把存在已知缺陷的录像直接当成绝对正确的 Ground Truth。

## 五、CC 第一阶段任务

第一阶段先进行架构评估与迁移规划，不要一开始就大规模修改业务代码。

请重点回答：

1. 现有项目中，哪些玩法规则和状态是迁移必需的？
2. 哪些代码可以直接参考，哪些部分应该在 Godot 中重新实现？
3. AST 与依赖分析具体能解决哪些迁移问题？哪些工作用简单扫描就足够？
4. 如何保证战斗随机数、卡牌触发、战斗结果和关键决策行为在迁移后保持一致？
5. Godot 项目应如何划分 Battle Core、状态模型、数据层、表现层、存档和 UI？
6. 如何建立 Godot 自身的测试与回归机制，而不依赖长期维护 JS 引擎？
7. 如何实现 Web 导出，并通过 GitHub Pages 让朋友直接打开游玩？
8. 哪些问题必须在迁移前确认，哪些可以在迁移过程中处理，哪些可以直接留待迁移后解决？

第一阶段交付《Godot Migration Architecture v1》及必要的代码结构盘点、迁移清单和验证方案。

所有分析与工具建设都必须服务于实际迁移。不要为了证明架构方案的完整性而无限扩展调查范围。

## 六、迁移完成后的收口

当 Godot 版本通过玩法、回归、构建及 Web 发布验收后：

- Godot 成为唯一正式维护的游戏项目。
- JS 旧项目归档，作为历史参考，不再持续开发。
- 不再要求两个引擎长期同步或永久对账。
- 后续新玩法、Bug 修复、测试和发布统一在 Godot 项目中完成。

**最终原则：不是维护两套游戏，而是利用现有 JS 游戏的成果，完成一次有边界、可验证的 Godot 迁移，然后只维护 Godot。**
