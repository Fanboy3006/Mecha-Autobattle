# 多智能体任务派发规范（Model- & Harness-Agnostic Dispatch Protocol）

> **定位**：本规范是 `mecha-autobattle` 长期有效的**多智能体任务分级、派单模板、停止/升级条件与成本评估唯一权威规范**。
> **解耦原则**：本规范绑定的是**职责角色与工程不变量**，而非特定模型、IDE 或 Harness。无论当前由 Gemini Argon、Claude Code（Opus / Sonnet）还是其他模型担任**主 Agent（Lead / Architect）**，也无论由 DS4F（`deepseek-flash`）还是其他快速模型担任**执行子代理（Worker Subagent）**，均须遵守本规范。
> **与既有文档分工**：
> - 窗口生命周期、三层上下文防火墙与开机提示词 → 见 [`协作/多模型高效协作指南.md`](多模型高效协作指南.md)
> - 多线并行、文件锁与共享文档追加规矩（§12.1） → 见 [`协作/协作框架.md`](协作框架.md)
> - 代码模块地图、5 大状态唯一 Owner 与改码四大铁律 → 见 [`docs/实现/AI速查卡.md`](../docs/实现/AI速查卡.md)
> - 现行游戏规则与提案 7 节模板 → 见 [`docs/设计/AI速查卡.md`](../docs/设计/AI速查卡.md)

## 一、 角色抽象与职责边界（与具体模型解耦）

| 抽象角色 | 当前常见配置示例（可替换） | 核心职责 | 严禁越权行为 |
|---|---|---|---|
| **主 Agent**<br>（Lead / Architect / Feature Lead） | Gemini Argon · Claude Code (Opus / Sonnet) | 1. 界定问题、分析方案、拍板设计参数与验收口径；<br>2. 决定任务分级与派单路由（内置 `subagent` **仅限 T1/T5 只读探针**；T2–T4 施工**一律写入 `协作/派单/当前任务.md` 停下交跨窗口会话执行**）；<br>3. 维护真相源文档（`AI速查卡`、`协作/架构快照.json`、`协作/派单/当前任务.md`）。 | 严禁在主上下文裸读大段源码（`src/js/**`）、测试文件或大型录像 JSON；严禁把未收敛的设计不确定性直接甩给子代理摸索；**未获人类当场显式指令，严禁在主会话调用内置 `subagent` 直接执行 T2–T4 代码施工**。 |
| **执行子代理 / 跨窗口施工会话**<br>（Worker Subagent / Session） | 内置 `subagent`（仅 T1/T5 只读探针）· **跨窗口独立会话（T2–T4 施工）** | 1. 内置 `subagent` 执行 T1/T5 只读探针，返回带 `文件:行号` 的客观事实与证据（0 文件修改）；<br>2. 跨窗口施工会话读取 `协作/派单/当前任务.md`，在授权白名单内完成代码/文档施工并运行验证命令，回写 `协作/派单/最新交付.md`；<br>3. 触发停止条件时立即暂停并结构化上报。 | 严禁擅自更改设计目标、放宽测试断言、改变统计口径、顺手扩单修改范围外文件，或未获授权修改文件。 |
| **独立审查代理**<br>（Guardian Agent） | 独立 Argon / Opus 会话 · 独立审查子代理 | 1. 独立于施工会话，针对 `git diff`、`协作/架构快照.json` 与 `tests/arch.js` 做破坏性审查；<br>2. 验证核心不变量（确定性、Owner 边界、回放兼容）。 | 严禁既当 Worker 又当 Guardian（自改自审）；严禁替 Worker 修代码或改设计。 |

## 二、 任务分级与子代理（DS4F 等）派单决策规则

### 2.1 核心判断准则
决定一项工作是否交给子代理（如 DS4F），**严禁简单按「难度高低」或「代码行数多少」一刀切**。主 Agent 必须按以下四个维度综合判定：
1. **规格明确度（Clarity）**：输入、修改落点、边界条件和期望输出是否已无歧义？
2. **错误代价（Blast Radius）**：一旦改错，是否会静默污染 `ctx.rng`、默认路径基线、存档格式或公共接口？
3. **可验证性（Verifiability）**：是否有确定性的命令、断言或前后数字对照能当场证伪？
4. **预期返工成本（Expected Rework Cost）**：若子代理理解偏差，主 Agent 排查+重派的总耗时是否高于先探针或主 Agent 自理？

### 2.2 五类任务分级与派单决策总表

| 等级与任务类型 | 典型场景 | 是否适合子代理（DS4F） | 主 Agent 派单前必须完成的前置工作 | 推荐派单模式 | 中途检查 | Guardian 独立审查 | 完成标准（Exit Criteria） |
|---|---|---|---|---|---|---|---|
| **T1 · 只读探针与事实调查** | 查函数定义/调用链、配置消费者、角色/编成数据分布、测试报红根因、接口与文档现状 | **极适合（首选内置 `subagent` 直派）** | 明确待查问题、目标文件范围（查实现速查卡 §1 / `RouteMap.md`）及返回行数上限（通常 ≤20 行） | 主会话内置只读 `subagent`（**严禁改任何文件**） | 否（达标即停） | 否 | 给出精确 `文件:行号`、客观证据、未知项与结论边界；**0 文件修改** |
| **T2 · 边界明确的机械性/局部施工** | 文档同步、已知枚举/常量批量替换、明确的测试断言同步、独立 CSS/局部 UI 调整 | **适合（跨窗口按单施工）** | 确认改动无设计歧义；若原因未明（如测试报错未知），必须**先派 T1 探针出诊断，再写施工单** | **写入 `协作/派单/当前任务.md` 即停**，交跨窗口施工会话执行（除非人类显式要求同窗 `subagent`） | 否 | 仅触及 `src/` 时跑 `arch.js`；纯文档免 | 允许范围内修改完成 + 指定验证命令真实通过 + `git diff --stat` 无越界 |
| **T3 · 跨模块复杂施工** | 多文件特性落地、跨模块接口新增、旧机制迁移、联动测试修复 | **适合分阶段派发（禁整包甩锅）** | **必须拆分为 4 步**：① 内置 T1 探针摸清耦合点 → ② 主 Agent 拍板参数表、接口签名与文件落点 → ③ **写入 `协作/派单/当前任务.md` 停下交跨窗口施工** → ④ 验收 | 内置探针 `subagent` → 主 Agent 定案并写 `协作/派单/当前任务.md` 即停 → 跨窗口施工会话执行 | **是**（按 P0/P1 分阶段或接口先行） | **必须** | `协作/接口约定.md` 已先登记 + `build-src` & `verify-all`（23/23）全绿 + 前后数字对照 |
| **T4 · 高风险架构与核心逻辑变更** | 确定性/`mulberry32`、`ctx.rng`、伤害/命中核心公式、回放兼容、`协作/架构快照.json`、5 大状态 Owner 变更 | **受控执行（主 Agent 定死规格后交跨窗口落码）** | 主 Agent **必须亲自确定**：① 完整数学公式/状态机；② `战斗结构.*` 开关与 `开:false` 回退证明；③ 基线常数（如 `defaultPathBattleLogCount`）预期变化 | 先内置 T1 探针 → 主 Agent 写死 `协作/派单/当前任务.md` **即停** → 跨窗口受控施工 → Guardian 破坏性审查 | **是**（先验 `开:false` 逐字节不变，再验 `开:true`） | **强制必做** | `开:false` 基线零漂移 + `开:true` 新快照/签名对齐 + `tests/arch.js` 与 `verify-all` 全绿 + Guardian 通过 |
| **T5 · 研究、创意与方案比较** | 调研外部游戏机制、评估新玩法可行性、对比多套技术/阵型方案 | **仅限事实收集与利弊对照（严禁直接改码）** | 主 Agent 给出比较维度（如架构冲击面、耦合行数、体验收益）与候选方案框架 | 主会话内置只读调研 `subagent`（先交事实与对比表，等主 Agent/作者拍板） | 是（先审调研报告再定是否立项） | 否 | 产出带代码证据的可行性、耦合度与利弊对比表；**未经批准严禁动任何代码** |

### 2.3 五类任务执行细则
1. **T1 只读探针**：当主 Agent 需要源码事实时，立即直派。子代理必须严格区分「已验证的代码事实」与「尚待确认的未知项」，禁止只给模糊印象。
2. **T2 机械性施工**：若修改映射规则 100% 明确（如「将 9 处已知测试的 `SLOTS === 9` 改为 `8`」），直接派单施工；若只知道「某测试红了」，禁止直接派子代理「去把测试修绿」，必须先派 T1 查明报红原因，由主 Agent 判断是代码 bug 还是基线更新后再下施工单。
3. **T3 跨模块复杂施工**：禁止把「帮我实现某某新玩法」这种未收敛的需求直接丢给子代理自由发挥。主 Agent 定死设计目标、开关参数、模块接口和验收标准；**允许子代理在单个函数内部自主选择具体编码实现手段，但绝不允许子代理自行更改设计目标、接口签名或验收标准**。
4. **T4 高风险核心变更**：凡触及 5 张顶层规则表（改变 `rulesSignature`）、战斗核心管线或录像格式，主 Agent 必须在任务单中明确「何时必须暂停请求决策」以及「`开: false` 与 `开: true` 的双轨验证步骤」。
5. **T5 研究与方案比较**：子代理只负责盘点仓内耦合成本与客观利弊，产出结构化对比供主 Agent 与作者拍板，绝不「边调研边顺手改代码」。

## 三、 标准派单协议与最小任务模板

为减少每次派单的提示词冗余与 token 消耗，主 Agent 派单时**统一引用本规范与两份 `AI速查卡.md`**，不在提示词中重复粘贴长篇项目规矩。

### 3.1 模板 A：T1 / T5 只读探针最小模板（目标 ≤12 行）

```markdown
【角色与模式】只读探针（T1/T5），工作目录 `F:\DSH-mecha\mecha-autobattle`。**严禁修改任何文件或运行写入命令。**
【调查目标】<一句话写清要查明的具体问题或要对比的方案维度>
【必查范围】<列出具体文件或目录，如 `src/js/20-战斗计算.js`、`src/js/30-射程.js`>
【输出要求】（严格 ≤N 行）：
1. 事实与证据：给出精确 `文件名:行号`、函数名、关键表达式或数据分布；
2. 未知项与边界：明确哪些内容在指定范围内不存在或未找到消费者；
3. 停止条件：拿齐上述证据即刻停止搜索并返回，禁止全仓漫游。
```

### 3.2 模板 B：T2 / T3 / T4 施工任务最小模板（写入 `协作/派单/当前任务.md` 交跨窗口施工会话执行）

> **★ 铁律（单轨制）**：主 Agent（Architect）对于 T2 / T3 / T4 施工任务，**只负责将任务书写入 `协作/派单/当前任务.md` 并立即停下汇报**，交由人类另开的跨窗口施工会话执行；**未获人类当场显式指令，主 Agent 严禁调用内置 `subagent` 直接改码施工**。

```markdown
【任务等级与目标】<T2/T3/T4>：<一句话目标> | 最终交付物：<修改的源文件 / 文档 / `协作/派单/最新交付.md`>
【背景与前置必读】先读 `docs/实现/AI速查卡.md` 与 `协作/多智能体派单规范.md` §3.3/§4；<补充本单 1~3 个必读文件>
【允许修改范围】<精确列出白名单文件清单>
【禁止修改内容】严禁手改 `index.html` / `src/artifact-fragment.html` 生成物、严禁改 `10-数据.js` / `85-播放.js` 时序 / `mecha-tactics`、严禁触碰白名单外文件、严禁自动 `git commit`。
【不变量与接口约定】
- 先在 `协作/接口约定.md` 末尾按 §12.1 追加登记新接口/字段，再动源码；
- 开关要求：<`战斗结构.XXX.开 = false` 时与改前逐字节一致；记录字段仅实际触发时写入>
- 纯读约束：预告/UI/枚举/统计调用前后 `ctx.rng` 步数 = 0；
- 基线要求：<说明 `defaultPathBattleLogCount` 与 `rulesSignature` 应保持不变还是按规矩同步>。
【验收标准与必跑命令】
1. <本单专项数值/行为/三层反馈断言>；
2. 顺序真实运行：`node tools/build-src.mjs` → `node tools/build-src.mjs --check` → `node tools/verify-all.mjs`（必须 23/23 全绿）。
【歧义与停止条件】遇规则歧义、接口冲突或同一问题经 2 轮实质修复仍红，立即按《多智能体派单规范》§4 停止并上报证据。
【汇报与交付格式】返回 ≤20 行摘要：1. 修改文件与接口登记项；2. 关键前后数字对照；3. 必跑命令真实输出与新签名/基线值；4. 范围外发现或待拍板项。
```

### 3.3 八条派单与执行底线纪律（强制生效）
1. **探针与施工严格隔离（内置 `subagent` 仅限只读探针）**：主会话内置 `subagent` **仅用于 T1/T5 只读探针与内存测算（0 文件修改）**；凡涉及 T2/T3/T4 施工修改，主 Agent **一律只写 `协作/派单/当前任务.md` 并停下等人类另开窗口执行**（除非人类当场显式要求同窗直改）。未完成事实调查前，不得将模糊问题包装成施工单。
2. **任务不明先调查**：遇到需求边界不清或报错原因不明时，先走 T1 探针缩小包围圈，严禁直接扩大施工范围试错。
3. **范围外问题「只记不改」**：子代理在探针或施工中发现白名单外的历史 bug、旧注释或架构债务时，**只能在交付摘要中单列一行报告**，严禁顺手扩展任务去改无关文件。
4. **代码现状 ≠ 设计意图**：当设计规则不明确或文档与代码不一致时，子代理必须暂停相关修改并提供源码证据上报主 Agent，**严禁把当前代码的既有行为（或 bug）自动当成设计意图固化下来**。
5. **严禁篡改裁判以求绿**：子代理**绝对不得**为了让测试通过而擅自更换测试目标、放宽断言阈值、删减检查项、跳过测试或篡改统计口径。若既有测试因合法的新规格（如阵型格数变更、默认队规则升级）需要更新，必须在任务单中有主 Agent 的显式授权并附前后对照。
6. **未跑严禁报绿**：任何未在当前执行环境中**实际运行并看到退出码 0** 的测试或构建命令，严禁在交付报告中声称「已通过」或「已验证」。
7. **局部通过 ≠ 完整验收**：涉及 `src/**` 或 `tests/**` 的施工，绝不能以 `build-src.mjs` 构建成功或单个测试文件通过代替完整的 `node tools/verify-all.mjs` 全量门禁验收。

## 四、 子代理（DS4F 等）停止条件与升级机制

为防止子代理陷入无限搜索、盲目试错或越权修改，同时避免对简单明确的问题制造繁琐审批，制定以下分级停止与升级规则：

### 4.1 五条强制停止与升级触发器（Stop & Escalate）
1. **两轮实质性修复未果（Two-Attempt Substantive Fix Cap）**：
   - **触发条件**：针对同一个测试失败或运行错误，经过 **2 轮有实质性逻辑区别的修复尝试**后问题仍未解决（或按下葫芦浮起瓢引发新红项）。
   - **动作**：立即停止第 3 轮盲目尝试；在汇报中列出「① 报错原文与位置；② 第一轮与第二轮各改了什么及为何无效；③ 当前最可能的根因与需主 Agent 拍板的选项」。
   - **低风险豁免（防过度流程化）**：若失败原因 100% 明确且属于低风险机械性遗漏（例如：改完源码忘了跑 `node tools/build-src.mjs` 同步 HTML、漏改了白名单内另一处同名常量、语法拼写笔误），**允许子代理直接连续修完跑绿**，无需停下请示。
2. **接口约定与实际实现冲突**：
   - **触发条件**：发现任务单、`协作/接口约定.md` 或 `AI速查卡.md` 中描述的函数签名、字段名、返回值与源码实际实现不一致。
   - **动作**：立即停止依赖该接口的后续修改，查明真实代码签名并上报主 Agent 确认以哪一方为准。
3. **被迫改变架构、设计意图或验收目标**：
   - **触发条件**：子代理发现如果不突破「允许修改范围白名单」、不改变 5 大状态唯一 Owner、或不修改任务单定死的设计规则/验收指标，任务就无法完成。
   - **动作**：立即暂停越界修改，保留已完成的安全部分，向主 Agent 报告阻塞点与最小必要扩权请求。
4. **触及核心不变量风险（Determinism / RNG / Replay / Snapshot）**：
   - **触发条件**：发现改动会导致表现层消耗 `ctx.rng`、引入非确定性遍历/时间戳、在 `开: false` 时仍改变默认路径 `ctx.log` 条数，或导致 `tests/arch.js` 门禁报红且不属于任务单预期的签名更新。
   - **动作**：立即升级给主 Agent，严禁自行绕过 `tests/arch.js`。
5. **探针已足以回答问题（Probe Sufficiency Stop）**：
   - **触发条件**：只读探针已经定位到主 Agent 询问的精确代码位置、数据表项或因果链。
   - **动作**：立即结束搜索并输出精炼摘要，禁止顺着调用链无休止阅读无关模块。

### 4.2 失败分类汇报标准
当子代理因上述条件暂停并升级给主 Agent 时，必须将问题归入以下 4 类之一，方便主 Agent 秒级决策：
- `[F-SPEC 规格歧义]`：文档/任务单未定义某边界情况，需主 Agent 拍板规则；
- `[F-ARCH 边界受阻]`：需修改白名单外文件或触及状态 Owner 限制，需主 Agent 授权扩围；
- `[F-BASE 基线漂移]`：确定性记录数、`rulesSignature` 或既有测试断言受新规则影响变化，需确认是否属实并授权更新基线；
- `[F-BUG 疑难缺陷]`：两轮实质修复未解的逻辑冲突，附现场证据交主 Agent 诊断。

## 五、 总成本与效率评估规则（Cost & Efficiency Governance）

主 Agent 不能因为子代理（如 DS4F）单次调用单价低就无脑外包一切，必须核算**任务全生命周期总成本**：

$$\text{任务总成本} = C_{\text{主Agent规划与写单}} + C_{\text{子代理执行Token与耗时}} + C_{\text{上下文交接与验单}} + P_{\text{返工}} \times C_{\text{重派与排查}} + C_{\text{Guardian审查}}$$

### 5.1 三路派单路由判据（何时直派 / 何时探针先行 / 何时主 Agent 自理）

| 路由策略 | 适用判据 | 为什么总成本最低 |
|---|---|---|
| **路由 1：直接派单一次闭环**<br>（Direct Single-Shot Dispatch） | 1. 属于 T1 探针或落点 100% 明确的 T2/中小型 T3；<br>2. 主 Agent 已掌握精确文件名与接口，写单成本极低（≤15 行提示词）；<br>3. 预期一次跑通率高，几乎无返工风险。 | 省去多轮往返交接，主会话上下文只增加 ≤20 行回传摘要。 |
| **路由 2：低成本探针先行 → 主定方案 → 再派施工**<br>（Probe-First, Two-Stage Dispatch） | 1. 属于跨模块 T3、高风险 T4，或主 Agent 尚不清楚源码精确行号與耦合面；<br>2. 若直接派施工，子代理会在大文件里盲搜试错，极易触发返工。 | 先花极小成本（1 次只读 T1 探针，≤20 行返回）把不确定性归零，再由主 Agent 一次性写准施工单，**消灭高昂的施工返工成本**。 |
| **路由 3：主 Agent 自行分析或直接处理**<br>（Lead Self-Handle） | 1. 纯规则推导、架构权衡、任务拆分或几行以内的顶层协作文档微调；<br>2. **不违反「主会话禁裸读大源码/大JSON」铁律**；<br>3. 若写派单提示词 + 等待子代理启动 + 验单的开销反而大于主 Agent 直接改 3 行文档。 | 避免「为了改 5 行文档写 50 行派单说明」的本末倒置。 |

### 5.2 成本核算纪律
1. **严禁编造数据**：主 Agent 与子代理严禁编造未实际采集的 token 消耗数字、耗时秒数或成本比例；也不得仅凭模型名称武断声称某模型一定更快或更准。
2. **经验沉淀优化**：当某类任务在实际协作中出现连续返工（如漏改 `SLOTS` 硬编码测试点、漏同步 `协作/架构快照.json`），主 Agent 应将该高频踩坑点沉淀进派单模板或速查卡的检查清单中，持续降低后续同类任务的返工率。
