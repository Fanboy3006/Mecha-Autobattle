## Q1 开关表

### Q1.1 怎么测的（探针与口径）

一个临时探针（`godot/tests/_probe_rt1.gd`，跑完已删）在 headless 里：

1. `DataLoader.install()` 装数据；
2. **肉鸽节点战选项** = `GameSession._build_battle_options()` 再并上 `_附加战斗选项()`（施工单 §Q1 指定的口径）；
   同时另跑一遍**真路径** `NodeResolver.开战(state, 条目, "", 附加)`（生产里节点战实际走这条）；
3. **快速测试选项** = 直接走真路径 `GameSession.开始快速测试战斗("秘银", 20261013)`，取回来的 `battle_ctx.选项`；

5. 每个 ctx 上逐个调 19 个开关函数，打印返回值。

三套选项的**键**（实测输出，`[A2b] / [A3] / [A4b]`）：

```

> 顺带发现（供 RT-2a 参考）：生产里**节点战并没有用 `_build_battle_options()` 的结果** ——
> `session/battle_flow.gd:204` 算了一遍缓存，下一行 `:206` 却调用 `NodeResolver.开战(...)`，由 `core/run/node_resolver.gd:372-377`
> 用 `RelicSystem.build_battle_options(state)` 自己重建选项再并 `附加选项`。所以两份选项本来就已经在漂：
> `_build_battle_options()` 里显式写的 `卡牌流转` 在节点战里**根本没传**（`[A3] ctx.选项 键 = ["秘银v03","战术卡牌","单机牌组"]`）。
> 因为 `秘银v03` 也会把 `卡牌流转v01开` 带成真，**取值没差**，但「两处各写一份」这件事是真的。
>
> 还要留意：`_battle_options_cache` 在节点战那条路上算完就没再用（`battle_flow.gd:204-205` 赋的值，`:206` 之后没人读）。
> 这也是 RT-2a 抽 `SessionBattleOptions.生产()` 时最该先收口的一处。

### Q1.3 三处需要写进决策表的事

（其中逐条打过回合号的那一场 = 秘银 / 20261013，4 条全部在第 1 回合；其余 8 场只统计了条数，没逐条打回合号。）
新模式的牌（上排专属 / 下排公有 / 衍生）走的是 `衍生牌置入`、`待入库`、`主武器卡`、`武器栏` 这些类型，**不会**写 `发牌`。

**是哪一条路径发的？** 单场逐条打印每条 `发牌` 的前一条事件（探针 `[D]` 段，秘银 / 20261013）：

```
[D] 第 1.0 回合 · 触发条件码=CMD_TURN2_OR_ENEMY3 · 牌=战术点名 · 前一条=攻击/ · 文本=〔发牌〕满足「第 2 回合起或场上敌机 ≥ 3 台」→ 获得战术牌【战术点名】…
[D] 第 1.0 回合 · 触发条件码=SPEC_HIT               · 牌=破甲引信 · 前一条=发牌/ · 文本=〔发牌〕满足「我方特种命中敌机后」→ …
[D] 第 1.0 回合 · 触发条件码=MITH_MARK              · 牌=SRT 突击接力 · 前一条=发牌/ · …
[D] 第 1.0 回合 · 触发条件码=ANY_MISS               · 牌=幻影反击 · 前一条=攻击/ · …
```

→ 第一条紧跟一次 `攻击`、其余三条紧跟 `发牌`（同一次 `检查条件发牌` 里循环发出来的），
**实际点火的是 `core/battle/flow.gd:322` 的 `Btl.检查条件发牌(ctx, "攻击后", …)`**。

### Q2.3 结论：**C（会产生事件，也会改变数值）**

| 项 | 实测证据 |
|---|---|
| 会产生事件 | 每场 4 条 `类型: 发牌`（9 场 36 条）。删掉旧牌池后这些记录会**整批消失** → 原生样例必须重录（= 施工单里的「闸门 G」） |
| 会改变数值 | `气势` 25 → 100（每场）；`战术手牌`/`待触发战术牌` 张数在变；`战况计数.满手牌推迟数` 会被这些发牌写（`card_pool.gd:533-551`） |
| **不改**战斗结果 | 打出的这 4 张牌落在 `ctx.战术手牌` 里，而**新模式没有任何代码会去打它**（`已打出战术牌` 9 场恒 0；`打战术牌` 的唯一 UI 入口在老手牌栏，见 Q3）。`气势` 在新模式里也只被旧池的触发条件读（`card_pool.gd:465`），`当前战术=总攻` 由 `CMD_ALL_OUT`（下排公有牌）置，与 `气势` 数值无关（`card_effects.gd:215`） |

**具体路径（走得到的三条，按实测点火顺序）**：

1. `core/battle/flow.gd:322` `Btl.检查条件发牌(ctx, "攻击后", …)` —— **实测点火**（36 条全在这里）。
2. `core/battle/morale.gd:24 → :43` `气势变动后发牌` → `检查条件发牌(ctx, "气势变动")` —— 每条 `加气势` 都会调（`calc.gd:598/740/855-863`），
   本次 9 场因为 `战术手牌` 已到 `手牌总上限=10`（`card_pool.gd:514-517` 走「满手牌推迟」）没再产出记录。
3. `core/battle/flow.gd:50-51`（回合开始 `候补补位` + `检查条件发牌("回合开始")`）与 `core/battle/setup.gd:90`
   （回合结束 `检查条件发牌("回合结束")`，因为 `endTurn` 在新模式由 `phase_flow.gd:144` 调用）—— 两处都在跑，本次没触发。

**走不到的一条**：`card_exec.gd:151`（`打战术牌` 之后的条件发牌）—— `打战术牌` 在单机牌组下没有 UI 入口（见 Q3）。
**不算旧池但同门的**：`fac_cb.gd:116`（手动 TRANS-AM）—— 它发的是旧池的牌，但触发者是玩家按钮，本次 9 场自动回合没走。

> 给 RT-3 闸门 G 的量化口径：**删旧牌池 → 每场少 4 条 `发牌`（9 场样例维度上，原生样例的单场事件数会 −4 左右）**，
> 并且 `气势` 会从「25→100」变成「恒 25（或 0，取决于是不是还建气势）」。RT-2d 的白名单已经不记 `气势`（施工单 §RT-2d），
> 所以只有 `发牌` 那 4 条会影响逐条对拍。

**问：`data/js/*.json` 现在是不是直接手改的？** —— **是**，三条证据：

1. **修改时间**（`Get-ChildItem godot/data/js`）：只有两个文件不是 M1/M2 那次导出的时间戳 ——

   若是重跑导出，`manifest.json` 一定会被一起重写 —— 它没变，说明那次是**手改**。
3. **那次改的正是本单 RT-4 要动的键**：`git show 9d9f8bb -- godot/data/js/71-改动-4-战斗结构.json` 的 diff 就是**整块新增**
   `"单机牌组": { "开": false, … }`（27 行，含 `"开": false`）。也就是说这个键当初就是**手写进去的**，不是 JS 导出的。

**问：重跑这个脚本会不会把手改内容冲掉？** —— **会，而且是整目录删掉重写**：

```js
rmSync(OUT, { recursive: true, force: true });   // godot/tools/export_data.mjs:74
mkdirSync(OUT, { recursive: true });
```

`OUT` 默认 = `godot/data/js`（`:14`）。所以只要它跑成功，`71-改动-4` 的手写 `单机牌组` 块、`94-零件.json` 的手改、

```

exit = 1        → checkSealed() 会 throw「JS 参考版与 js-reference-final 不一致」
$ git diff --name-only js-reference-final -- . ':!godot' ':!.github' ':!协作'

只要有人把那两个非游戏文件提交/还原，`export_data.mjs` 就会跑通并**立刻冲掉手改**。
