## §2 问题清单（附证据与修法）

### §2.1 P1（正式口径下必现）

#### P1-1 装甲共享池让「无视 N% 装甲」完全失效
- **路径**：正式口径 `单机牌组 = true` → `Params.装甲共享池(ctx) = true` → `resolveAttack` 按 `round(effArmor(def) × defMul(def))` 初始化池（`calc.gd:754-757`）→ 每段把 `装甲池` 传进 `dmgCore` → `dmgCore` 里算出来的 `A`（**已扣 `ignoreArmorPct`**，`calc.gd:298-305`）在池分支里**根本不用**，`base = W − min(池, W)`（`calc.gd:339-348`）。
- **影响**：天人【斩断扭曲】/【反坦克刺刀】（`celestial_v01.gd:1823`）、秘银 v0.3 的 `无视装甲比例`（`mithril_v03_cards.gd:102-103`）在正式战斗里全部等于没写。全仓没有一条测试覆盖 `ignoreArmorPct`。
- **修法**：池的初值改成与 `dmgCore` 的 `A` 同一个函数，例如抽出 `Calc.有效抵消甲(def, w)`（`effArmor × defMul × (1 − ignoreArmorPct)`），`resolveAttack` 初始化池和 `dmgCore` 老公式都调它。补一条测试：甲 1000、`ignoreArmorPct = 0.5`、`500×6`，池应为 500。

#### P1-2 哈雷路亚可以打太阳炉牌 / 天人势力牌（违反【双人格】）
- **路径**：`Btl.打出精神或公有牌` 在天人分支直接 `return CelestialV01.打出太阳炉牌 / 打出势力牌`（`btl.gd:2513-2517`），而人格门槛 `CelestialV01.卡不可打原因(..., 从公有)` 排在后面的 `btl.gd:2538`，永远走不到。两个打出函数自己也没查 `公有牌可打`（`celestial_v01.gd:556-623`）。
- **测试为什么没发现**：`test_celestial_v01.gd:1021-1030` 只断言了谓词 `公有牌可打()` 的返回值，没有从打出入口真打一次。
- **修法**：两个打出函数开头补 `if not 公有牌可打(ctx, u): return {"成功": false, "原因": …}`；更好的做法是 P2-2 的统一谓词。补一条「哈雷路亚打太阳炉牌 → 失败」的集成测试。

### §2.2 P2（规则缺口 / 高概率 Bug，建议先写测试确认）

#### P2-1 断路器 3 旁路：`grant` 型支援主武器卡
- `Btl._执行支援卡` 遇到 `w.grant` → `Flow.resolveAction("grant")` → 直接 `t["主武器已销毁"] = false`（`btl.gd:2164-2172` → `flow.gd:188-196`），**不走 `DeckFlow.再动`**：不查锁、也不写锁。
- 数据里确实有这种武器：`ALLY_T[4]` 菲娜（月球王国·指挥）的「再动」，`grant: true`，Lv20 解锁。如果它在单机牌组里被装成主武器卡，就能给本回合已经再动过的队友再恢复一次。
- `fac_mith.gd:203` 的「倒下接力」也是同样的直写，不过它在秘银 v0.2 下已经退役。
- **修法**：`flow.gd` 的 grant 分支在 `Params.单机牌组_开(ctx)` 时改调 `DeckFlow.再动(ctx, t, w.name)`。

#### P2-2 手牌「纯可打」有两份判定
- 门面判下排公有牌能不能打，只看 `身份对口 + 战意`，筹码牌另走一支（`game_session.gd:2808-2822`）。它**没有调**内核打出时会查的 `AtxFaction.不可打原因`（每回合限 1 次 / 入库条件）、`ClassCards.不可打原因`（按打出者验入库条件）、`CelestialV01` 的人格 / 只限天人 / 入库条件。
- **后果**：卡面亮着可打，点下去报「打不出来」；自动换人发动时还可能挑中哈雷路亚。这直接违反规范 §二.1 的铁律。
- **修法**：内核提供唯一的纯读谓词 `Btl.公有牌不可打原因(ctx, u, card) -> String`，把 `打出精神或公有牌` 里那串门槛原样搬进去；打出入口和门面视图都只调它。上排的 `武器栏 / 副武器 / 大招` 已经是这个模式（`game_session.gd:2983/3013/3040`），把下排也拉齐即可。

#### P2-3 攻击后钩子被直调 `Calc.resolveAttack` 绕开
- 正式代码里有 8 处直接调 `Calc.resolveAttack`，不经过 `Flow.resolveAction`：`atx_three.gd` 5 处、`fac_atx.gd:623`、`btl.gd:399`（自爆）、`mithril_v02_cards.gd` 1 处。
- `Flow` 结算完会做：`CelestialV01.标记被攻击 / 受击后 / 消费首击减伤`、势力攻击后、击破记账等（`flow.gd:301-340`）。这几处直调要么自己补一部分（例如 `atx_three.gd:1941-1944` 自己记击破），要么干脆不做。
- **具体后果**：混编队（`默认分队 = "混编"`）里，ATX 的「再来一把 / 冷枪」打过的敌机**不会**被标 `本回合被攻击过`，刹那随后打它还能触发【武力介入】。
- **修法**：见 §3 Phase 2，做一个「单次攻击服务」，所有攻击都走它。

#### P2-4 钳爪 / 「本回合被刹那打」靠读日志 + 意图目标推断
- `武器打完后` 用 `_目标敌(ctx, u)`（出牌时**指定的**目标）配 `_末次攻击命中`（倒着扫日志找最后一条「攻击」）来决定给谁挂效果（`celestial_v01.gd:1948-1975`）。
- 只要攻击被护卫或援护改了目标，或者是范围 / 多目标，命中的那台和挂效果的那台就可能不是同一台。
- 这个函数本来就有 `_结果` 参数，但没用上。**修法**：从 `_结果` 里取实际命中的目标和命中段数。

#### P2-5 敌方意图预告与「横向掩护 / 铁壁护卫」不同源
- `Btl.算意图` 只用 `Boss.bossAction → Ai.enemyAction` 的原始目标（`btl.gd:1628-1694`）。`Ai` 里只并入了塔斯克的【掩护】（`ai.gd:257-261`）。
- 结算时 `Flow` 还会调 `Btl.嘲讽`，里面又有 `ClassCards.横向掩护接管`、`铁壁护卫` 两条改目标规则（`btl.gd:125-138`，调用点 `flow.gd:270`）。
- `btl.gd:165` 的注释说「预览路径（`ctx._预览中` / `算意图`）只读检查」，但全仓没有任何地方设置 `_预览中`，`算意图` 也不调 `嘲讽`。
- **修法**：`算意图` 对单体攻击走一次只读的 `Btl.嘲讽`（设 `_预览中`，不扣次数），把最终目标写进意图。补测试：打出【横向掩护】后，意图目标应该等于实际承伤者。

### §2.3 P3（小问题 / 隐患）

1. **`SubDeck.放入` 的字符串 id 陷阱**：传 `String` 时是在**库里**找同 id 的牌再 append，结果是同一个字典引用出现两次（`sub_deck.gd:153-169`）。目前没有调用方这样用，建议删掉这条分支，或者明确报错。
2. **断路器 3 的锁有 6 处复位写入**（`deck_flow.gd:177-178`、`atx_chips.gd:175/188`、`atx_three.gd:922`、`btl.gd:1751`）。在「单机牌组开、卡牌流转关」的组合下，非 ATX 机体的 `本回合再动已用` 永远不会被复位。正式口径不会出现这个组合，但说明「谁负责复位」没有唯一归属。建议只保留 `DeckFlow` 一处。
3. **`deck_flow.gd:513` 是死分支**：和 491 行判的是同一个条件。
4. **`btl.gd:511 static var _实例号计数`** 是进程级全局状态（只在没有 ctx 时兜底用），跨场次时会影响确定性，建议去掉兜底。
5. **`λ还原武器` 用 `MithrilV03Cards.卡(原)` 重建原卡**（`deck_flow.gd:1132-1150`），卡上的运行期字段（`当前冷却` 等）会被重置。要确认 λ 开关一次会不会把武器冷却刷掉。
6. **`ClassCards.卡表()` 没有缓存**，每次调用都重建 18 张，`按名` 在命中 / 伤害修正的热路径上（`class_cards.gd:68`）。其它卡表都用了 `static var _表`，这里漏了。
7. **「伊奥利亚的遗产」对正处于 TRANS-AM 中的机体也能用**：重置 `本场已开TRANSAM` 后可以立刻再开一次，`transam剩余回合` 被重置回 3，效果是延长而不是第二次使用。需要设计确认（`celestial_v01.gd:974-983`）。

## §3 解耦方案（按优先级）

### 核心问题：通用内核直接点名势力模块

由 `Godot-AST依赖清单.json` 统计：**核心通用模块 → 势力模块共 213 处引用**（不含注册表 `fac.gd` 自身 33 处、`session` 37 处、`presentation` 2 处）：

| 通用模块 | 引用的势力文件数 | 引用次数 |
|---|---|---|
| `btl.gd` | 15 | 76 |
| `deck_flow.gd` | 11 | 53 |
| `calc.gd` | 8 | 31 |
| `setup.gd` | 10 | 14 |
| `deck_builder.gd` | 4 | 13 |
| `flow.gd` | 4 | 9 |
| `card_effects.gd` | 6 | 8 |
| `ai / boss / data_fn / params / reach / roster_manager` | 各 1–2 | 共 9 |

另有 3 条势力 → 势力的横向引用：`atx_duo → CelestialV01`、`atx_faction / atx_three → MithrilV03Cards`。

已有的 `Fac` 注册表（17 个钩子）只接入了 4 个旧势力（`fac_cb / mith / moon / seed`）。ATX v0.3、天人 v0.1、秘银 v0.3 全部**绕过注册表**，直接写进 `Calc.resolveAttack` 和 `hitRate` 的连环乘子、`DeckFlow.大招不可打原因 / 打出大招` 的 if 链、`Btl.开始我方阶段` 的逐个调用里。照现在的写法，接殖民卫星军、影世界、月球王国 v0.x，每个都要改这 6–8 个核心文件，而且是在同一段热代码里追加分支。

### Phase 0（先做，0.5 天）：给 RouteMap 加一条棘轮审计
在 `build_godot_routemap.mjs` 加规则 ⑤：**通用内核文件 → 势力文件的边数不得超过基线（213）**。新增的势力逻辑只能走注册表。数字只许往下降，`--check` 超标即红。现有四条规则只查跨层依赖，这一类耦合目前完全看不到。

### Phase 1（殖民卫星军之前）：势力插件接口
把 `Fac` 升级成「势力模块注册表」，每个势力一个模块，实现可选钩子（不实现 = 中性值）：

```
阶段初 / 我方阶段末 / 敌方阶段初 / 开局初始化
命中修正(att, def, w) / 暴击修正 / 闪避加成 / 伤害倍率(att, def, w) / 受伤倍率
```

- `Calc` 把 `ClassCards × CelestialV01 × AtxDuo × …` 这串乘子换成 `Fac.汇总伤害倍率(ctx, att, def, w)`，按**固定注册顺序**迭代。乘法交换，但每步都 `J.round`，所以顺序必须和现在的调用顺序一致，才能保持数值逐字不变。
