## 3. 一条线的标准流程（开工 → 交付）

1. **开工前**：读 `CLAUDE.md` + 本文档 + 自己的交接文档；看 `协作\分工看板.md` 第 1 节，确认**生成物闸门**（第 4 节）没被别人占着。
2. **做的过程中**：只写自己那列的文件；**新数值不许自己发明**（战棋有的逐字照抄并标 `文件名:行号`；查不到的写「初稿」）。
3. **收工前**（缺一不可）：
   - `node tools/build-src.mjs`（重建生成物）；
   - `node tools/build-src.mjs --check` → 必须「检查通过」；
   - **二十套测试**（smoke / sim / battle_ui / commands / run / comp / map / **art_icons** / **audio** / boss / heal / relic / rank / balance / grid / faction / **tuner** / **录像** / **分析** / **上报**）全过；
   - 改了自己的线档（`协作\任务板.md` **追加**一段 + `协作\协作日志.md` **追加**一条 + 看板自己那一行）；
   - `git add` **只加自己那条线的文件** → 提交（`[标签]` + 中文）；
   - 在 `协作\分工看板.md` 第 2 节把自己的**状态**改成「已交付（commit 短哈希）」。
4. **交付报告**（给统筹 / 作者）：**怎么试 + 真实测试输出**（哪几套、最后一行是什么、关键数字）。
   红了的套数要说清「是不是别人的线引起的」以及证据。
5. **统筹验收**：在**干净检出**（或临时 `git worktree`）上跑 `--check` + 二十套，翻一遍改了哪些文件，确认没夹带别人的文件，
   然后才向作者报告。

## 4. 生成物闸门（串行规则，防互相覆盖）

`index.html` 和 `src\artifact-fragment.html` 是**所有线共用**的生成物，谁重建都会覆盖一次。

- **同一时刻只允许一条线在动生成物**。开工前先看 `分工看板.md` 第 1 节的**闸门**字段：
  - 空着 → 把自己的线名填进去，开工；
  - 写着别人 → **等**（或先做不碰生成物的部分）。
- 收工提交后，把闸门字段清空。
- 如果提交时发现**生成物里混进了别人未提交的素材**（例如 `art/`、`audio/` 有人正在改），
  用**临时 `git worktree`** 按已提交的素材构建，再拷回来（2026-10-11 前三条势力线就是这么做的），并在报告里注明。
- 提交后若发现 `--check` 红、且原因**不是自己**的改动 → 不要覆盖别人的工作，写进看板第 3 节，交给统筹。

### 9.2 新增红线（第 7 节之后同样有效，违反就算失败）
1. **绝不覆盖别人正在改的文件**：任何形式的 `git checkout -- <别人的文件>`、`git restore`、`git reset --hard`、

## 12. 两条实战规矩（2026-10-12 立，都是交付线里验证过的）

### 12.1 共享文档里有别人的未提交段落时，怎么只提交自己那一节
**问题**：`协作\任务板.md`、`CLAUDE.md` 这类共享文档，常常同时躺着**几条线**的未提交追加段
（例如机设线的 `[机设]` 一节、演出线的改动）。直接 `git add` 会把别人的段落一起提交（夹带），
按框架第 5 节 A2 把追加段留在工作区又会让自己的交付缺文档。

**做法（2026-10-12 三层反馈线实战验证）**：
1. 对自己的那份**最终内容**：`git hash-object -w <临时文件>` 拿到 blob 号；
2. 用 `git update-index --cacheinfo 100644,<blob>,<路径>` **只把「HEAD + 我这一节」这一版**放进暂存区；
3. `git commit` 后，**别人的段落原样留在工作区**（`git status` 里仍是 `M`），
   绝不 `checkout` / `reset` / `stash` / 覆盖；
4. 提交前用 `git diff --cached --numstat` 与 `--ignore-cr-at-eol --numstat` 对比，确认是**纯追加**（`X 0`）；
5. 报告里写清「我暂存了哪一节、别人的哪些段落没动」。

### 12.2 分步提交时，中途提交可以不自洽，但**必须写明**
如果一件工作分多次提交，**中途某个提交可能是「源文件中间态 + 按最终态构建的生成物」**（`--check` 在它自己身上会红）。
**规矩**：① HEAD 必须自洽（`--check` 与二十条测试全绿）；② **该提交的说明里必须照实写明「它自身 `--check` 会红 / 原因」**；
③ 后续用**新的提交**补齐（`747e189` 就是这么做的）；④ **不许 `--amend`** 去粉饰历史。

## 13. 不要把「可以试」当成硬要求；不要为边缘情况加约束（作者 2026-10-12）

**背景**：统筹在任务书里写「A6 隧道可以试『一端在起点侧、一端在出口侧』」——这是**可选项**，
但执行线把它做成了**硬约束 + 专门断言**，为少数不满足的图反复调参/加特判。作者看到的是「在跟边缘情况较劲」。

**规矩（所有线适用）**：
1. 任务书里凡是写「**可以试 / 建议 / 可选 / 初稿**」的，**都不是必须达成的要求**；
   做了发现不划算就**放弃并写一句理由**，**不要为了它加约束、重试或特判**。
2. **验收只认**：① 作者明确提出的要求；② 任务书里给出的**具体指标**（数字/表格）；③ 现有测试不许放宽。
   其他一切都属于「实现细节」，**不许为了覆盖率或极端情况新增硬断言**。
3. 测试口径：**测规格，不测极端情况**。宁可「少数个案不完美」，也不要「为完美而加重试/特判/复杂规则」。
4. 若你已经为某个可选花样写了代码或断言 → **删干净**，并在交付报告里**单列一句「砍掉了哪些为了边缘情况的约束/断言」**。

## 14. 共享工作区**不许切分支**（2026-10-13 事故后立规）

**事故经过**：夜里某条线为做实验建了分支 `try-stepfun-录像` 并**切了过去、没切回来**。
随后三条线**都以为自己在 `main`**：统筹的《对局上报接收端》文档、录像线的测试走法修复、上报线的客户端 ——
**三笔提交全部落在实验分支上，`main` 落后三个提交**。统筹发现时 `main` 上少了这三笔。
**修复**：`git branch -f main HEAD`（快进；**没有 `checkout --` / `reset` / `stash` 任何人的文件**），再 `git switch main`（两分支同点，工作区一个字节没动）。
`try-stepfun-录像` 分支保留（内容已与 `main` 同点），但其存在**纯属事故残留**。

**规矩**：
1. **共享工作区的分支永远是 `main`**。任何线**不许** `git checkout` / `git switch` / `git branch -f` 改变它；
2. 要做分支实验 → **另开一个独立工作树**：`git worktree add <仓库外路径> -b <你的分支>`，在那里折腾，**别动主工作区**；
   用完 `git worktree remove`（工作树里也不许留 `.tmp-*`）；
3. **每次提交前先跑一条** `git branch --show-current`，看到的必须是 `main`；不是 → **立刻停下报统筹**，不要自己切回去；
4. 发现 `main` 少了别人的提交、或工作区不在 `main` → **报统筹**；`main` 的快进/对齐**只由统筹做**。

## 15. 共享工作区必须**始终可解析**（2026-10-13 事故后立规）

**事故经过**：某条线在改 `src/js/89-录像.js` 时，在一个模板字符串里直接写了反引号（`` `决策` `` 而不是 `<code>决策</code>`）——
**模板提前结束 → 语法错 → 拼出来的 `index.html` 解析不了**。影响：**其余三条线**（难度 / 出口 / 界面）的 `tests/*` 与 `verify-all` **全部跑不了**。

**做对的地方**（难度线）：发现工作区不可解析 → **没有去改别人的文件**，而是起了一个**隔离镜像**（HEAD 源码 + 只贴自己这条线的改动）继续测量，并**报告统筹**。这就是正确姿势。

**规矩**：
1. **存盘即完整**：改源文件时，**保存下来的中间状态必须语法完整**（模板字符串、括号、`</script` 这类尤其注意）。
   写完一段就**立刻跑一次** `node tests/smoke.js`（它才几秒）—— 它红了就是你刚写坏了。
2. **发现工作区不可解析 / 别人 WIP 让你红** → **用隔离镜像继续**（`git worktree` 或「HEAD 源码 + 只贴我的改动」那种镜像），
   **报统筹**，**绝不去改别人的文件**（也不要用 `checkout --` / `reset` 收拾别人的工作区）。
3. **统筹负责恢复共享工作区**：修掉或让作者那条线修掉语法错，然后**重建一次**（`node tools/build-src.mjs`）+ 冒烟（`node tests/smoke.js`）+ `--check`，
   确认「能解析、0 报错、同步」，再通知所有线回来。

## 16. 不变量要写成**关系式**，不许钉历史常量（2026-10-13）

**事故形状**：`tests/录像.js` 第 [8] 段原来断言「`simulate` / 练习 / 调参 三条路径的摘要 == **HEAD 那一版的常量**」。
这是拿**某一刻的历史数值**当**跨版本不变量** —— 于是**任何合法的平衡 / 难度改动都会让它变红**（2026-10-13：难度线改了 `71-改动.js` 的敌人强度，三条摘要就变了，套件直接红）。
决策线用**隔离镜像**（HEAD + 只贴别人未提交的 `40/60/70/71/80/90/92`）证明了「红因不是它自己」——**这个取证方法值得照抄**。

**规矩**：
1. **不变量一律写成同一构建内的关系式**，例如：
   - 「**开 / 关**录像，同一条路径结果逐字相同」；
   - 「**传 / 不传** `选项.调参`，结果逐字相同」（`tests/tuner.js` 第 [1] 段的真实意图）；
   - 「A 分支 / B 分支在**同一构建**下的差 = 预期差」。
2. **历史常量只能当「信息」**：打印出来、或写进 `协作\任务板.md` 的「本版基线」一节；**难度 / 平衡改动后由那条线更新基线**，**不许让它变成断言失败的理由**。
3. 涉及**平衡 / 难度**的改动，**本来就会改** `simulate()`、战斗记录、胜率、回合数 —— 交付说明里**照实写「这些数字变了、为什么」**，**绝不许写「逐字不变」**。
4. 怀疑「红因不是自己」时：**隔离镜像**（HEAD + 只贴你改动的文件，或只贴别人未提交改动）跑一遍对比 —— **别去改别人的文件，也别用 `checkout --` / `reset` 收拾工作区**。

## 17. 生成物提交**必须来自隔离副本**（2026-10-13 事故后立规）

**事故**：某条线在**共享工作区**直接 `node tools/build-src.mjs` 重建，然后把两份生成物单独提交（`f14b468`）——
那一刻工作区里还有**别人在制的源码**，于是 `index.html` **固化了别人的未提交代码**，而**那些源码不在这个提交里**。
后果：**HEAD 自己就不一致** —— 干净检出跑 `node tools/build-src.mjs --check` **红**；
在 HEAD 上跑任何测试会崩（实测 `TypeError: this.开合并 is not a function`，因为源码里没有那个函数）。**别人的镜像也一起红。**

**规矩**：
1. **要提交生成物时，必须在隔离副本里重建**：临时 `git worktree` 到**当前 HEAD**（或 `HEAD + 只贴你这条线的文件`），在那里跑 `node tools/build-src.mjs`，
   **只把两份生成物**（`index.html` / `src/artifact-fragment.html`）带回你的提交。**参考做得对的那一笔**：`0eaf69e`（出口线）。
2. **绝对不要**在共享工作区重建后直接提交生成物 —— 那时工作区几乎一定混着别人的在制源码。
3. **共享工作区的生成物允许是「过期」的**（多条线并行时必然如此）：`--check` 在**共享工作区**红是**正常**的；
   但**每一笔提交自己的 HEAD 必须自洽**（在该提交上 `--check` 绿）。
4. `_probe/` 下**别人的目录不许动**（哪怕是「看起来是空的」）—— 各线只用自己新建的唯一目录（例：`_probe/econ-*`）；
   误在两个目录里跑过 `build-src` 的，**报统筹**，由统筹转告那条线重跑一次重建。

## 18. 提交前自查暂存区（2026-10-13 第三次「连带提交」事故后立规）

**今天三起同类事故**：
1. 某线用 `git commit --only <paths>` —— 它**无视暂存区、提交工作区内容**，把别条线的在制 WIP 带进提交；
2. 某线 `git commit` 时**没核暂存区**，把别人**已 `git add`** 的 3 个文件（`tests/分析.js` / `tools/战报分析.mjs` / `协作/战报分析-口径.md`）一起提交；
3. 共享工作区出现「**先 `git add` 再 `git commit`**」的窗口期：这段时间**谁提交都会把别人已暂存的文件带走**（分析线就是这么被带走的）。

**规矩（所有线）**：
1. **提交前必跑**：`git diff --cached --name-only`（或 `--numstat`）**逐行核**，确认暂存区里**只有你这条线的文件**；发现别人的 → **停下报统筹**，别硬提交（**不许 `--amend`**）。
2. **优先精确提交**：`git commit -- <你的路径…>`（它提交**工作区里这些路径**，绕开暂存区里的别人）；或干脆在**隔离副本**里提交。
   ★ **绝不要**用 `git commit --only <paths>`（今天第 1 起事故就是它）。
3. **暂存窗口纪律**：`git add` 与 `git commit` 之间**不要做别的写操作 / 不要跑会改仓库的命令**；多条线并行时，**尽量把「暂存 → 提交」压到最短**。
4. **共享文档**（`任务板.md` / `协作日志.md` / `CLAUDE.md` / `接口约定.md`）一律照 **§12.1** 只暂存「HEAD + 你这一节」，**绝不整文件 `git add`**。
