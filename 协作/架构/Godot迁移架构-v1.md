> **作者**：CC（Godot 架构与迁移负责人） · **日期**：2026-10-15 · **状态**：第一阶段交付，待作者验收

## 0. 结论（一页）

1. **能迁，且边界清楚。** 真正要「照规则移植」的只有 **战斗内核 + 规则参数 + 肉鸽局外规则**，约 **7,900 行有效代码**（全仓 15,400 行有效代码的一半）；其余一半是 DOM 界面、录像 / 上报 / 调参室等工具，在 Godot 里**重写或不迁移**。
2. **确定性已经用实测证明可以对齐。** `godot-spike/` 在 **Godot 4.7.2** 上把 JS 的 `mulberry32` 移植成 GDScript，对 7 个种子 × 2000 次抽取**逐位一致**；`Math.round` 与稳定排序两处语义差也已补齐并通过测试。
3. **Web 发布路线已实测打通。** 同一个 spike 导出成 Web（单线程、不需要特殊响应头），在 Chromium 里加载约 1.5 秒，**浏览器里算出的校验和与无界面测试完全相同**（`182751003`）。产物 39.5 MB，gzip 后约 10 MB，GitHub Pages 会自动 gzip。
4. **对账只做一次，不做永久双引擎。** 从 JS 一次性导出一批「黄金样例」（固定输入 + 命令脚本 → 结构化事件流 + 末状态），冻结进 Godot 仓库当测试夹具。Godot 通过全部样例 = 玩法语义迁移完成；之后 JS 归档，样例成为 Godot 自己的回归基线。
5. **实测发现、必须照做的三条硬规则**：
   - 黄金样例里**不能存 JSON 小数**：Godot 的 JSON 解析会丢浮点精度（spike 里 5 个探针有 1 个解析后变了值）。随机数存成 uint32 整数，其他浮点存 IEEE-754 位串。
   - 规则代码**不能用 Godot 内置 `round()`**：`round(-2.5)` 是 `-3`，JS 是 `-2`；**不能用 `sort_custom` 排序有并列的数组**：它不保证稳定。统一走 `JsCompat`。
   - **必须打包中文字体**：Web 版没有系统字体，spike 截图里中文全是方框。
6. **迁移前只需要作者定 3 件事**（§9.1）：行动方针去留、Godot 仓库放哪 / 是否公开、公开发布的素材与角色版权口径。

## 2. Q1：哪些玩法规则和状态是迁移必需的

### 2.1 必须迁移（玩法语义，ARGON 已在试玩中确认在跑）

**战斗**
- 阵型：正交 4×2 八格、阻挡 / 对位 / 相邻、出击上限公式（`05`）
- 单位：模板 → 面板（等级、档位、职业映射、词条）（`10` `11` `12` `40` `70`）
- 结算管线：命中 / 暴击 / 伤害 / 减免 / 护盾 / 武器 CD / 多段命中 / 标定（`20`）
- 射程：5 类射程、范围落点、职业判定（`30`）
- AI：选武器、选目标、修理阈值（`50`）
- 回合流程：回合开始钩子、行动序、增援波次、动作结算、胜负、回合上限（`60-2` `60-3`）
- 气势与战术卡牌：三层牌池、初始牌 / 条件触发、`战况计数`、打牌结算、手牌上限、打牌后复查发牌（`60-1` + `71-5` 卡牌表）
- Boss：大技能间隔、半血换阶段（`61`）
- 七势力钩子与特色：SEED、流星孤立、月国光环 / 残月、TRANS-AM、ATX 打空、秘银标定接力（`72-1..5`）
- 现行开着的结构机制：职业排位、兰斯战线、Feena 主动攻击、敌人机制、词条、标定经济

**肉鸽**
- 开局与分队、带队核心、等级 / 经验 / 希望（`90-1` `90-3`）
- 地图：分层正方形生成、最短路、推进剂、必经点、双出口（`91`）
- 7 种节点结算、黑市、事件（`90-4`）
- 招募券、招募、晋升算价、3 选 1 选牌（`90-2` `90-5`）
- 战后回血、HP 继承、通关 / 失败（`90-5` `90-6`）
- 藏品 58 件（开战注入、获取）、零件 13 件（`93` `94`）

**状态**：`ctx` / 单位 / `RUN` 中被上述规则读写的字段（§1.4），以及每条随机流的种子公式（§5.2）。

### 2.2 迁移但重做形态

| JS 现状 | Godot 形态 |
|---|---|
| `ctx.log`（中文文本 + 字段） | **结构化事件流**（只保留字段，文本由表现层按事件生成）；它同时是对账、战报、回放的唯一来源 |
| 录像（操作流 + 中文对账串） | **种子 + 命令流**（`命令 = {回合, 阶段, 类型, 参数}`）；重放 = 用同一内核重跑 |
| 决策日志（`8b`，屏级枚举） | 命令层的「可选命令枚举」+ 实际选择，与命令流同源 |
| `localStorage` 存档 v4 | `user://` 下的 JSON 存档（Web 上落到 IndexedDB），带 `schema_version` |
| 战报统计（`84`） | 从事件流汇总，照移统计口径 |

### 2.3 不迁移

| 项 | 理由 |
|---|---|
| 动作QTE（`开:false`）、演出 demo | 未启用 |
| 调参室（`95-1..3`） | 开发工具；Godot 里需要时用数据文件 + 测试替代 |
| 上报（`8a`，Apps Script） | 与发布目标无关 |
| 旧录像格式、`tools/replay.mjs` 的跨版本兼容（P1.1 兼容档等） | Godot 不读 JS 录像 |
| 所有 `开:false` 的旧分支、兼容旧存档 v1~v3 | 只实现现行规则 |
| **行动方针（5 种方针）** | **待作者定**（§9.1）。若决定取消，Godot 直接不实现，内核按「全军突击」语义写死 |

## 3. Q2：哪些直接参考，哪些重新实现

| 类别 | 做法 | 理由 |
|---|---|---|
| 内容数据（角色、敌人、编成、卡牌、藏品、零件、5 张参数表） | **机器导出**：加载 JS 页面，从 `window.__game` 把表直接 dump 成 JSON，进 Godot 的 `data/` | 不手抄、不靠 AST 解析对象字面量；运行时 dump 拿到的就是游戏实际用的值 |
| 战斗内核、局外规则（L2、L3 规则部分） | **逐函数对照移植成 GDScript**，函数名和结构尽量对应 JS，方便对账时定位 | 这是对账对象，结构相近能把「找第一处分叉」的成本压到最低 |
| 数值工具函数（四舍五入、排序、取整、随机） | 统一走 `JsCompat` / `Mulberry32`，**已实现并测试** | 见 §5 |
| 卡牌效果（`打战术牌` 里 46 个 `case`）、触发条件 | 移植时**改成数据驱动**：卡牌表声明「效果操作 + 参数」，内核只实现一小组效果操作 | 新卡只加数据；数值进数据表。语义不变，用黄金样例证明 |
| 势力钩子（17 个生命周期 / 数值钩子） | 照移成「势力模块注册钩子」的同构结构 | JS 结构本身合理，直接沿用 |
| 界面（L6 全部）、播放时序（`85`）、图标（`78` 矢量绘制） | **重写**为 Godot 场景；图标用现有 `tools/render-icons.mjs` 先渲染成 PNG 导入 | DOM 代码对 Godot 没有复用价值 |
| 表现层统计（`84` 战报统计） | 照移统计口径，输入改成事件流 | 统计规则是玩家可见语义 |

## 4. Q3：AST 与依赖分析能解决什么，什么用简单扫描就够

| 问题 | 工具 | 状态 |
|---|---|---|
| 片段之间谁调谁、内核有没有偷读上层（迁移切分的依据） | 解析整体拼接后的源码（acorn），按行号归属片段 | **已完成**：`依赖清单.json`，结论在 `迁移地图.md` |

## 5. Q4：如何保证随机数、卡牌触发、战斗结果和关键决策一致

### 5.1 一致性契约

**同一份输入（阵容、敌方、种子、选项）+ 同一串命令 → 同一串结构化事件 + 同一个末状态。** 「同一」的判定：

1. 事件流逐条比对**结构化字段**（类型、单位、目标、伤害、命中、暴击、卡牌 ID、气势前后等），**不比中文文本**；
2. 每回合末对关键状态做摘要比对（各单位 HP / 护盾 / 增减益 / 冷却、气势、手牌 ID 列表、待触发列表、`战况计数`、**随机数已抽次数**）；
3. 不一致时报告「第一处分叉」：哪一回合、哪一条事件、此时随机数抽到第几次。

### 5.2 随机数

- **生成器**：`Mulberry32`（GDScript），已对 7 个种子 × 2000 次抽取与 JS **逐位一致**（含 `0`、`2^31`、`2^32−1` 等边界种子）。
- **战斗**：每场一条流，种子 = 开局种子；JS 的内核**只有 5 处抽随机数**（`20-战斗计算` 4 处：命中 1 处、暴击 3 个分支，其中 1 个分支属于已关闭的动作QTE；`60-战斗-1` 1 处 50% 判定），所以抽取顺序完全由事件顺序决定，移植时只要事件顺序对，随机数就对。
- **局外**：15 处 `mulberry32(…)` 调用点（多为 `种子 + 层×613 + 场次×37 + 格号×17 + 偏移` 的形式），分布在 `90-1/2/3/4/5`、`91`、`93`、`94`。迁移清单里**逐条登记种子公式**，Godot 用同一公式。
- **纪律**：内核与规则代码里不准出现 `randi()` / `randf()` / `RandomNumberGenerator`，只用 `Mulberry32`（Godot 侧门禁照抄 `tests/arch.js` [2] 的思路）。

### 5.3 已知的语义陷阱（扫描结果 + 处理）

| 陷阱 | JS 现状 | Godot 处理 | 验证 |
|---|---|---|---|
| 四舍五入 | 规则代码约 104 处 `Math.round`（`20` 24 处、`70` 17 处、`60-1` 16 处…） | 一律 `JsCompat.js_round`；Godot `round(-2.5) = -3`，JS 是 `-2` | **spike 已测**（129 个样本） |
| 稳定排序 | 内核 + 局外 29 处 `.sort()`（`91-地图` 9 处、`60-1` 6 处） | 并列可能出现的排序一律 `JsCompat.stable_sort` | **spike 已测** |
| 浮点 | JS 全程双精度 | GDScript `float` 也是双精度，运算结果一致；**但 JSON 解析会丢精度** | **spike 已测**：样例文件不存 JSON 小数 |
| 整数位运算 | `>>> 0`、`| 0`、`Math.imul` | GDScript `int` 是 64 位，按 32 位手动掩码 | **spike 已测**（`Mulberry32.imul`） |
| 对象遍历顺序 | JS 对象「整数样键排前、其余按插入序」；30 处 `Object.keys` / `for…in` | Godot `Dictionary` 只按插入序 → 移植时逐处确认键的类型，整数样键改成显式排序 | 黄金样例覆盖 |
| 字符串比较 / 排序 | JS 按 UTF-16 码元 | Godot 按码点；**只在 BMP 外字符（如 emoji）上不同** | 规则代码不按字符串排序即可（移植时检查） |

### 5.4 黄金样例（一次性从 JS 导出，冻结进 Godot）

**格式**（每个样例一个 JSON 文件）：
```
{ "id": "battle/default-path/047", "kind": "battle",
  "input": { "我方": […], "敌方规格": […], "种子": 20261010, "选项": {…}, "藏品": [] },
  "commands": [ { "回合": 1, "阶段": "指令", "类型": "打战术牌", "参数": "C_CMD_1" } ],
  "expect": { "events": [ { "类型": "攻击", "单位": "B1", "目标": "E2", "伤害": 4051, … } ],
              "turn_digests": [ { "回合": 1, "rng_steps": 14, "units": […], "气势": 50, "手牌": […] } ],
              "result": { "结果": "胜", "原因": "敌方全灭", "回合": 2 } } }
```
- 数值：整数照存；浮点存 IEEE-754 位串；随机数存 uint32 —— **不存 JSON 小数**（实测原因见 §0）。
- `rng_steps`：导出脚本在**副本**里给 `mulberry32` 包一层计数（不改 JS 仓库源码）。
- 藏品场景：导出脚本在副本里显式设置 `肉鸽.RUN.藏品`（绕开 DEBT-06，不需要修 JS）。

**覆盖范围（目标约 300 个）**

| 组 | 内容 | 数量 |
|---|---|---:|
| 默认路径 | 47 场标准编成 × 默认五人队（即 `2788` 那一组） | 47 |
| 势力 | 7 个分队 × 6 个代表编成 | 42 |
| 卡牌 | 32 张卡各至少一个「打出」脚本；15 个触发条件码各至少一个「发牌」场景；满手牌推迟 | ~60 |
| Boss / 增援 / 词条 / 敌人机制 | 每个 Boss 与机制至少 2 场 | ~40 |
| 藏品 | 58 件按「开战注入」类别抽样 | ~30 |
| 局外 | 地图生成（多种子 × 4 层）、节点结算、券掷骰、招募 / 晋升、3 选 1 候选 | ~80 |

**样例的身份**：它们是「迁移那一刻 JS 的行为快照」，不是绝对真值。Godot 跑不过时，先看是不是 JS 自身的已知缺陷：是 → 登记到「已接受差异表」并由 ARGON 签字，不改 JS；否 → 修 Godot。

## 6. Q5：Godot 项目结构

### 6.1 分层原则

- **Battle Core / Run Core 是纯逻辑**：`RefCounted` 类，不继承 `Node`、不碰场景树、不读 `user://`、不读时间、不用引擎随机数。输入是数据 + 命令，输出是事件 + 新状态。可以在 `--headless` 下直接跑测试。
- **表现层只读**：场景订阅内核产出的事件流来播放动画、飘字、刷界面；玩家操作只能变成「命令」交给内核。表现层不改状态。
- **数据与逻辑分离**：所有数值在 `data/` 的 JSON 里，内核只读。
- **会话层（Session）是唯一的接线点**：持有当前 `RunState` / `BattleState`、接收命令、调用内核、分发事件、负责存档与录像。

### 6.2 目录

```
mecha-godot/
├─ project.godot                     # 渲染器 = Compatibility（Web 只支持 WebGL 2）
├─ export_presets.cfg                # Web 预设：单线程（variant/thread_support=false）
├─ core/                             # ★ 纯逻辑，headless 可测
│  ├─ util/        rng.gd（Mulberry32）· js_compat.gd（js_round / stable_sort）

│  │               relics.gd · parts.gd
```

### 6.3 存档

- `user://save.json`，`{ "schema_version": 1, "game_version": "…", "rules_version": "…", "run": {…} }`。
- Web 上 `user://` 落在 IndexedDB：**无痕模式不保存**、iframe 嵌入需要第三方 Cookie（Godot 官方文档原话），界面上要提示。
- 存档只存 `RunState` 的数据，不存派生量；读档后用内核重算派生量。

### 6.4 回放 / 决策日志

- 一局 = `{ 种子, 分队, 规则版本, 命令流 }`。重放 = 用同一内核从头执行命令流，比对事件摘要。
- 「可选命令枚举」由命令层统一产出：界面用它决定哪些按钮可点，决策日志直接记「当时的可选集 + 实际选择」。JS 里决策日志和界面各写一套、彼此对不齐的问题（DEBT-02、FIX-1/2）在结构上就不会出现。

## 7. Q6：Godot 自己的测试与回归，不依赖长期维护 JS

| 层 | 内容 | 何时跑 |
|---|---|---|
| 单元 | `Mulberry32`、`JsCompat`、射程 / 阵型几何、伤害公式、卡牌效果操作 | 每次提交 |
| **黄金样例** | §5.4 的约 300 个样例：逐条事件 + 回合摘要比对 | 每次提交 |
| 确定性 | 同一样例跑两遍逐字节相同；随机数抽取次数一致 | 每次提交 |
| 边界门禁 | `core/` 不准引用 `Node` / 场景 / `user://` / 引擎随机数 / `round()` / `sort_custom`（简单扫描） | 每次提交 |
| Web 冒烟 | 导出 → Playwright 打开 → 跑一个固定样例，校验和必须等于 headless 结果 | 每次发布前 |
| 人工验收 | 作者试玩清单（§10 每个里程碑的出口条件） | 里程碑 |

**测试框架**：先用零依赖的自制入口（`tests/run_tests.gd`，spike 已在用：`extends SceneTree`，退出码 0/1）。只有当测试数量让它难以维护时，再引入 GUT 或 GdUnit4。

**脱离 JS 的方式**：黄金样例在 M1 一次性生成后**提交进 Godot 仓库**。迁移完成后，玩法有意改动时，由 Godot 自己重新生成受影响的样例（Godot 版的导出命令），在提交里写明「哪些样例因哪条规则变化而更新」，并由 ARGON 签字。JS 仓库从此不再参与。

## 8. Q7：Web 导出与 GitHub Pages

### 8.1 已实测（`godot-spike/`）

| 项 | 结果 |
|---|---|
| Godot 版本 | **4.7.2**（2026-08-18 维护版，当前最新稳定版） |
| 语言 | **GDScript**（官方文档：Godot 4 的 C# 项目**目前不能导出到 Web**） |
| 导出方式 | `godot --headless --export-release "Web" build/web/index.html`，单线程（`variant/thread_support=false`） |
| 产物 | 9 个文件、约 39 MB；`index.wasm` 39.5 MB，**gzip 后约 10.1 MB** |
| 浏览器 | Chromium（WebGL 2，Compatibility 渲染器）加载约 1.5 秒（本地服务），无报错 |
| 一致性 | 浏览器里 `Mulberry32(20261015)` 2000 次抽取的校验和 = **182751003**，与 headless 结果相同 |
| 发现的问题 | **中文显示为方框** → 必须打包 CJK 字体 |

### 8.2 为什么 GitHub Pages 可行

- 单线程导出（Godot 4.3 起提供）**不需要** `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` 响应头，而 GitHub Pages 不能自定义响应头 —— 这条正好绕开。
- GitHub Pages 会自动 gzip（Godot 官方文档把它列为「提供实时压缩」的主机），wasm 实际传输约 10 MB。
- 代价：不能用线程（本项目是回合制，不需要）；音频走默认的 Sample 模式，**音频效果器（混响等）在这个模式下还没实现**（官方文档），音乐和音效需要按此设计。

### 8.3 发布流水线

```
push main
  └─ ci.yml：下载 Godot 4.7.2（缓存）→ 导入 → run_tests.gd（含黄金样例）→ 失败即停
  └─ pages.yml：安装 Web 导出模板（只解压 web_nothreads_release.zip，约 10 MB）
                → export-release "Web" → actions/upload-pages-artifact → actions/deploy-pages
```
- 版本号与「规则版本」写进导出的页面标题和存档。
- **账号限制**：免费账号只能从**公开仓库**发布 Pages；GitHub Pro 可以从私有仓库发布，但**站点本身仍是公开可访问的**（GitHub 文档）。所以「朋友打开链接就能玩」= 知道链接的任何人都能玩。

### 8.4 字体与包体

- 中文字体用思源黑体 / Noto Sans SC 一类开源字体，按游戏实际用到的字符**做子集**（全量 CJK 字体 10 MB 以上，子集通常 1~2 MB）。子集化用构建脚本从 `data/` 和界面文本里收集字符。
- 音乐：现有 `audio/SUNO/*.mp3` 需要按 Web 包体重新评估（转 OGG、降码率、按场景懒加载）。

## 13. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 内核里隐藏的遍历顺序 / 并列排序依赖 | 少量样例对不上，定位慢 | 回合摘要 + 随机数次数能把分叉定位到单条事件；`stable_sort` / 显式排序一律从严 |
| 卡牌效果数据驱动化时改变了语义 | 卡牌组样例失败 | 先「照搬 46 个 case」让样例全过，再重构成数据驱动，两步分开 |
| Web 包体与首屏加载 | 朋友手机网络慢 | 字体子集、音频懒加载；必要时预压缩 |
| 迁移期间作者又想加玩法 | 双引擎同时改 | 新玩法只在 Godot 里做，排在 M4 之后 |
| 公开发布的版权口径 | 发布受阻 | D3 提前定 |
